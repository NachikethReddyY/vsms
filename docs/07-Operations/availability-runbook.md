# VSMS availability and recovery runbook

## Service objective

VSMS targets 99.9% availability, excluding approved scheduled maintenance. This is an objective, not a claim: production uptime must be measured before the team reports it as achieved.

The initial recovery objectives are:

- Recovery point objective (RPO): no more than 15 minutes of committed database data.
- Recovery time objective (RTO): restore core registration, queue, screening, and review APIs within 60 minutes.
- Scheduled maintenance window: Sunday 19:30-20:30 UTC (Monday 03:30-04:30 Singapore time).

The infrastructure in `infrastructure/availability.yaml` supports these objectives with two replaceable API tasks, continuously restarted report, domain-event, and optional lifecycle-email workers, rolling ECS deployments, Multi-AZ RDS, encrypted Redis failover, 30-day database backup retention, S3 versioning, readiness monitoring, and alarm-driven deployment rollback.

## Production prerequisites

Before deploying, the operator must provide:

1. A VPC with at least two public and two private subnets across different Availability Zones. Private subnets need NAT access or VPC endpoints for ECR, CloudWatch Logs, Secrets Manager, and required external providers.
2. A Route 53 public hosted zone and separate dashboard and API hostnames.
3. An ACM certificate in the deployment region for the API hostname and an ACM certificate in `us-east-1` for CloudFront.
4. An immutable API image in ECR, referenced by its `sha256` digest. Mutable release tags such as `latest` are rejected.
5. Cognito callback and logout URLs matching the production dashboard hostname.
6. A Secrets Manager secret containing the versioned encryption keyring JSON. Do not put the keyring value in parameter files or source control. Database, Redis, runtime database, and JWT secrets are generated by Secrets Manager during stack creation.

The template generates separate database-owner and `vsms_runtime` credentials, Redis credentials, and JWT material in Secrets Manager. Application tasks receive only the restricted runtime database URL. The owner URL is reserved for controlled migrations and recovery. Do not place secret values in CloudFormation parameter files, shell history, logs, or source control.

The stack also creates an encrypted, retained EFS filesystem for administrator-created dump files. Its access point is mounted only by the API task over encrypted transport, and the task role can write only through that access point.

## Initial deployment

1. Bootstrap the GitHub OIDC provider, CloudFormation service role, ECR repository, and the scoped roles in `infrastructure/github-oidc-roles.yaml`. GitHub must not contain long-lived AWS access keys.
2. Build the API image from `backend/Dockerfile`, scan it, push it to ECR, and record its immutable digest.
3. Validate `infrastructure/availability.yaml` with CloudFormation in the target AWS account.
4. Create the stack with `ApplicationServicesEnabled=false`. The database, Redis, and EFS resources are private and must not be made publicly accessible.
5. From an approved migration environment, retrieve the migration URL and runtime credentials from Secrets Manager without printing them. Apply migrations with the database owner, then execute `backend/prisma/runtime-role.example.sql` as the owner with the generated runtime password. Never give the owner URL to an application task.
6. Update the stack with `ApplicationServicesEnabled=true`. This starts two API tasks and one copy of each enabled worker only after the restricted role exists.
7. Configure the `staging` and `production` GitHub environments. Production requires at least one reviewer, main-branch protection, and its own concurrency lock. Add the role, stack, region, API URL, and smoke-test variables described in the deployment report.
8. Configure Cognito with the exact HTTPS callback and logout URLs, then run the authenticated acceptance workflow.
9. Create and download one administrator backup, verify its checksum, and confirm that replacement API tasks see the same EFS-backed backup list.
10. Start availability measurement only after the application, database migrations, Cognito integration, alert subscription, and recovery checks pass.

## Normal release without planned downtime

Database and application changes use an expand-and-contract sequence:

1. Merge an approved pull request into `main`, which starts `.github/workflows/deploy.yml`.
2. The workflow runs CI and the migration compatibility check, builds one image, generates its SBOM/provenance, scans it, and records the immutable digest.
3. Staging assumes short-lived OIDC roles, registers the candidate migration task, and applies only backward-compatible schema expansion before updating services.
4. The workflow waits for the API and every enabled worker, verifies `/ready`, runs a safe authenticated API operation, checks alarms, and publishes the frontend entry point last.
5. The protected production environment requires approval and repeats the same steps using the exact staging image digest.
6. Any failed post-migration gate restores the previous application image. The migration itself is not reversed automatically; expand-and-contract preserves compatibility with that previous image.
7. The workflow uploads a release manifest containing actor, approval environment, commit, digest, migration, service, timestamps, test evidence, and rollback metadata.
8. Remove obsolete database fields only in a later release after rollback to the previous application is no longer required.

If a migration cannot be made backward compatible, classify the release as scheduled maintenance and obtain approval before consuming the maintenance exclusion.

## Automatic recovery behavior

- ECS maintains at least two API tasks and replaces tasks that stop or fail the load balancer health check.
- ECS uses `/health` as process liveness, while the load balancer and Route 53 use the database-aware `/ready` route before directing traffic.
- The load balancer sends requests only to ready tasks and drains connections during replacement.
- API 5xx rate, p95 latency over one second, unhealthy targets, worker failures/dead letters, stopped tasks, RDS resource pressure, RDS availability events, and synthetic readiness notify the encrypted operations SNS topic. Selected alarms also stop and roll back ECS deployments.
- RDS Multi-AZ performs managed database failover and retains transaction recovery data and automated backups for 30 days.
- ElastiCache runs a primary and replica with automatic failover, encryption in transit, authentication, and seven days of snapshots.
- S3 versioning preserves prior frontend objects, while CloudFront continues serving cached static assets during an origin interruption.
- Fatal Node.js errors terminate the affected task. ECS performs the restart; the application does not attempt unsafe in-process recovery.
- Screening stations with a previously downloaded encrypted event pack can temporarily record supported screening results offline and synchronize them later.

Offline operation is business-continuity protection, not proof that the API was available. API downtime must still be recorded by the availability measurement.

## Database recovery

Never restore a production dump over the active production database from the administrator API.

For an RDS failure or data-corruption incident:

1. Freeze releases and record the incident start time.
2. Determine the latest known-good time from audit records and managed backup metadata.
3. Restore RDS to a new isolated instance using point-in-time recovery or a snapshot.
4. Restrict the restored instance to recovery operators and validate migrations, constraints, and critical row counts.
5. Run read-only checks for events, participants, registrations, queues, screening results, sync actions, and audit logs.
6. Update the database URL secret to the isolated replacement only after validation.
7. Force a rolling ECS deployment so tasks receive the new secret value.
8. Run authentication and core-workflow smoke tests, then reopen service.
9. Preserve the failed database for investigation according to the retention and incident-response policy.
10. Record actual RPO and RTO and create follow-up actions when either objective was missed.

The repository's `backup:postgres` command is an additional operator-controlled export. It requires an absolute `VSMS_BACKUP_DIR` outside the repository and creates a SHA-256 checksum and critical-table row manifest. `restore-postgres:test.sh` accepts only an explicitly acknowledged isolated database whose name ends in `_test`.

## Frontend rollback

1. Identify the last known-good S3 object versions.
2. Restore `index.html` first, followed by any non-hashed runtime files it references.
3. Invalidate `/index.html` in CloudFront.
4. Do not delete newer hashed assets until all clients have aged out of the prior release.

## Maintenance records

For every scheduled maintenance period, record:

- approving administrator and reason;
- announced start and end time;
- expected affected workflows;
- recovery point verified before work;
- deployed image digest and migration identifier;
- validation evidence and actual completion time;
- whether any downtime exceeded the approved window.

Unannounced or overrun maintenance counts as unavailable time. Security incidents, failed deployments, database failovers, and external-provider failures must not be silently relabelled as scheduled maintenance.

## Quarterly recovery exercise

At least quarterly:

1. Restore a production-equivalent backup into an isolated non-production account.
2. Verify checksum, schema migration state, constraints, and critical row counts.
3. Run the core authenticated workflow without transmitting real participant information.
4. Measure achieved RPO and RTO.
5. Delete the exercise environment securely and retain only redacted evidence.

Passing backup creation is not sufficient; a backup becomes a credible availability control only after a successful restore exercise.
