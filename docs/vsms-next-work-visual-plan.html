01

Four separate decisions control access.

The easiest way to understand the new design is to stop treating an account, an approval, a role, and a work shift as the same thing.

01 / ACCOUNT

Who are you?

Email, name, profile, and Cognito identity. Creating an account does not give operational access.

02 / APPROVAL

Are you trusted?

An administrator approves or rejects the account. Approval allows login but does not assign an event job.

03 / EVENT ROLE

What can you do here?

A role is assigned for one event: manager, registration, screener, reviewer, or support.

04 / DUTY

Where and when?

A shift and station assignment narrows the event role to a specific time and work location.

Plain language

A person may have an approved account but no event work. They can view their profile and wait for an assignment. They cannot open queues, screening, reviews, or event reports until an event role is assigned.

02

What exists today, and what must change.

The current system already has secure Cognito sign-in, event assignments, reporting foundations, hard deletion, audit logs, and SES referral email. The problem is that account roles and event roles overlap.

Current system

Global roles are required first

  • Public signup is disabled.
  • An administrator creates staff accounts.
  • Users receive global roles such as Screener or Reviewer.
  • The same user is then assigned again inside an event.
  • A role can unintentionally describe the person across every event.
  • The user profile is mostly read-only.
Target system

The event assignment grants the job

  • People can create their own account.
  • Every new account starts pending.
  • An administrator approves the identity only.
  • Operational roles are assigned separately for each event.
  • One person can do different work at different events.
  • The profile clearly shows approval, permissions, and assignments.
Why this requires a careful migration

The current backend checks Cognito groups, database roles, a derived system role, event creator ownership, and staff assignments. Those checks cannot be removed in one deployment. The safe order is to add the new memberships, backfill them, compare old and new decisions, move every endpoint, and only then remove the old role paths.

03

Administrator and manager are different jobs.

Administrator is a global platform responsibility. Event Manager is an operational responsibility limited to selected events.

Platform Administrator Whole system
  • Approve, reject, suspend, and reactivate accounts.
  • Revoke sessions and review platform audit history.
  • Create an event and appoint its first manager.
  • Permanently delete completed or cancelled events.
  • Protect the final active administrator account.

Does not automatically screen participants, review cases, operate queues, or read event analytics.

Event Manager Assigned events
  • Manage the event schedule, stations, and assignments.
  • Assign approved users to event roles.
  • View event operations and completed-event analytics.
  • Generate permission-controlled PDF and CSV reports.
  • See only events they manage.

Cannot approve accounts, create platform administrators, or permanently delete events.

Operational event roles One event at a time

Use granular roles so a general Staff role does not accidentally grant both registration and screening access.

REGISTRATION SCREENER REVIEWER SUPPORT EVENT_MANAGER
Staff or doctor?

Staff and Doctor may be profile categories, but they are not permissions. A doctor becomes a Reviewer only when assigned to that role for an event. Administrator must never be available as a signup choice.

04

The new user journey, step by step.

Signup proves identity first. Approval establishes trust. Event assignment grants work.

STEP 01

Create account

The user chooses Create account and enters credentials through Cognito.

STEP 02

Verify identity

Cognito verifies email, password policy, and MFA. The application does not store the password.

STEP 03

Pending approval

The local account is created without roles. The user can complete a profile and view approval status only.

STEP 04

Admin decision

An administrator approves or rejects the account and the decision is permanently audited.

STEP 05

Approved, no work

The user can sign in and view a No event assignments page. There is still no operational access.

STEP 06

Event role

An event manager assigns the approved user to a role for one selected event.

STEP 07

Shift and station

Where needed, a duty narrows the role to a shift, station, and assignment state.

STEP 08

Role-based workspace

The user sees only the pages and API operations permitted for that event role.

Pending

Profile, status, logout. No operational pages.

Approved

Account accepted. May still have no event work.

Assigned

Access only to permitted actions for the assigned event.

What happens to sign-in, refresh, logout, and passwords?
  • Keep Cognito Hosted UI for sign-in, signup, verification, MFA, and password recovery.
  • Add visible callback loading and safe failure states.
  • Wire the existing idle-timeout utility into the application.
  • Complete local logout and Sign out everywhere.
  • Correct documentation that currently describes local one-time refresh rotation.
  • Use a server-side invalid-before time so an administrator can invalidate existing sessions.

Privacy rule

Reports should contain aggregate information by default, not participant names. Small clinical groups should be suppressed, with a recommended threshold of fewer than five records.

What goes into the PDF and CSV?

PDF: event details, active filters, registration and attendance charts, queue and station charts, screening distributions, review and referral outcomes, generated time, metric definitions, a file hash, and deterministic written observations.

CSV: an explicitly selected aggregate dataset with spreadsheet-formula protection. It must not silently include participant identities.

Job states: Queued, Generating, Completed, Failed, and Expired. PostgreSQL stores claim leases, attempts, retry timing, filters, hashes, and requester details. Redis is not required.

07

Deletion becomes a reviewed operation, not one button.

The existing backend already performs a transactional hard delete for completed or cancelled events. The remaining work is impact visibility, two correctness fixes, and clearer cleanup status.

01Preview impactCount registrations, queues, screenings, reviews, files, emails, and reports.
02Show blockersStop if cross-event references or active report jobs make deletion unsafe.
03Explicit confirmationTyped event name, acknowledgement, current version, short-lived preview token.
04Delete transactionRecheck impact, retain immutable audit, remove operational records.
05Cleanup statusRemove files safely and show queued, completed, or needs-attention state.
Fix required

Review-signature cleanup

The cleanup service can request a review-decision-signature task, but the current database constraint does not allow that task type.

Fix required

Older synchronization rows

Rows with no event ID may still point to records from the deleted event. Cleanup must use collected entity IDs without touching unrelated rows.

What remains

Operational event data is permanently deleted. Immutable audit evidence remains, including who deleted the event, the event snapshot, the reviewed impact, and the confirmation method.

08

Email has three different responsibilities.

Using one provider for every message would require replacing working security controls. The safer first release keeps each provider responsible for the job it already handles best.

COGNITO

Identity email

Email verification, password reset, MFA, and account-recovery messages remain with Cognito.

GOOGLE SMTP

Application lifecycle

Signup received, approved, rejected, suspended, reactivated, event assignment, and backend-observed password-change notices.

AWS SES

Clinical referral

Keep the existing encrypted referral attachment, delivery callbacks, bounce handling, and reconciliation flow.

Important limitation

Google SMTP can confirm that Google accepted a message. That is a Sent state, not proof that the recipient received it. The interface must not claim Delivered unless a real delivery signal exists.

How Google SMTP should be configured
  • Use Nodemailer with Google Workspace OAuth2, TLS validation, timeouts, and bounded retry.
  • Keep OAuth credentials and refresh tokens outside Git.
  • Use a verified, allowlisted sender.
  • Extend the current notification outbox rather than build a second delivery system.
  • Store template and safe metadata, not reset tokens or sensitive message bodies.
  • Do not call SMTP inside the account-approval database transaction.

Yes, database tables need to change.

These changes have not been made. They must be reviewed before implementation because they affect authentication, authorization, reporting, and historical data.

  • Add approval state: Pending, Approved, Rejected.
  • Add access state: Enabled, Suspended, Disabled.
  • Add optional Staff or Doctor profile category.
  • Add session invalidation time.
  • Make employee number optional during signup.

Approval history NEW TABLE

  • Account being decided.
  • Approve or reject decision.
  • Administrator who decided.
  • Reason and decision time.
  • Immutable audit behavior.

Event authorization NEW TABLES

  • Event Membership connects a user to one event.
  • Event Membership Role stores granular event roles.
  • Staff Assignment becomes shift and station scheduling.
  • Remove global operational roles after safe backfill.

Report generation NEW TABLES

  • Report Export Job stores status, filter snapshot, attempts, and requester.
  • Report Artifact stores file location, type, size, hash, and expiry.
  • Existing immutable audit log records generation and downloads.

Email delivery EXTEND TABLE

  • Add email purpose and provider.
  • Add template name and version.
  • Add claim, retry, and next-attempt fields.
  • Keep referral-specific SES behavior isolated.

Cleanup and retirement MIGRATIONS

  • Add Deleted event-audit action.
  • Add analytics indexes.
  • Fix cleanup-task constraint.
  • Retire unused local password and refresh-session tables after confirmation.
Migration rule

Do not delete the current role fields first. Add new tables, backfill existing users and event assignments, validate the result, move each API route, and remove the old fields only after old and new authorization decisions agree.

Why implementation cannot safely start with the screens

The visual pages depend on a stable account state machine and event permission model. Building screens first would encode the current conflicting role system and create rework. The schema, transition rules, backfill, and endpoint authorization matrix must be approved first.
