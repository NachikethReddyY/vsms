01 — North star

Digitise a community vision-screening event without losing the ability to operate when the network does.

The Visual Screening Management System (VSMS) replaces paper forms, manual tracking, spreadsheet consolidation, and manual reporting. It must protect participant data while keeping registration, screening, review, referrals, dashboards, and reporting operational in real event conditions.

Definition of done

A secure cloud-enabled application that supports multi-station workflows, local offline capture, controlled synchronization, real-time operational visibility, and auditable handling of participant information.

Outcome

Fast, paper-light operations

Target a 50% reduction in registration time, a 90% reduction in paperwork, and 30% greater screening throughput.

Scale

One event, many moving parts

Design for up to 500 participants per event, multiple stations, and operational tracking from registration to referral.

Trust

Security is a feature

RBAC, audit trails, encryption, secure APIs, and OWASP Top 10 alignment are assessed requirements—not polish.

05 — Architecture, data & API

Build a connected system: responsive PWA → local queue → secure API → durable data.

Frontend
React + TypeScript responsive web app, with offline and synchronization capability. IndexedDB is suggested for offline storage.
Backend
Node.js + Express; JWT authentication is specified in the common project specification.
Database
The common specification says choose one: PostgreSQL. The deliverables brief frames a NoSQL / DynamoDB design principle and AWS-serverless option—make your chosen approach explicit and defensible in the report.
Data modelling
If using DynamoDB, model access patterns with partition keys, sort keys, GSIs and item collections—not joins and foreign keys.
Operational targets
API ≤ 1 second; 99.9% availability; offline capable; 500 participants/event; full audit trail.
Offline means fully functional

Users can view screens, enter data and navigate without any network connection.

Sync is a choice

Allow continuous syncing while online or a deliberate end-of-event synchronization mode.

Queue lifecycle

PENDING → PROCESSING → SUCCESS, or FAILED → RETRY. Retry failed background requests automatically.

No duplicate records

Repeated sync requests must not create duplicate screening results or other duplicate writes.

Minimum API surface

Auth — POST login, logout, refresh. Events — POST/GET/PUT/DELETE /api/v1/events. Participants — POST/GET/PUT /api/v1/participants. Screening — POST visual-acuity, refraction, colour-vision and eye-health endpoints. Sync — POST /api/v1/sync/batch.

06 — Evidence to submit

Package the implementation into a report, diagrams, code, deployment material and a tight live story.

10–12 page documentation Required

Include Executive Summary, Problem Statement, Business Requirements, Functional Requirements, Non-Functional Requirements, Use Case Analysis, Architecture Design, Database Design, API Design, Security Design, Testing Results, Deployment Guide, and Reflection.

Diagram pack Required

Submit a Context, Use Case, NoSQL Design, Component, Deployment, Sequence, Security Architecture, Offline Synchronization, and Secure API Design diagram.

Source + deployment material Required

Include frontend, backend, database scripts and deployment scripts. Make it possible for an evaluator to follow your configuration and reproduce the running system.

15-minute demonstration Required

Cover login, registration, screening workflow, offline mode, synchronization, dashboard and security controls. Plan a clean reset state and a believable failure/retry moment.

Sample data volume Plan for

10 events, 20 users, 500 participants, 2,500 screening results, 500 queue records and 5,000 audit logs.
